# 面试投递追踪

## 概述

帮助用户追踪求职投递的全过程：从投递新岗位、记录面试进度、到最终结果。所有数据存储在本地 JSON 文件中，通过自然语言交互完成增删改查。

**零成本架构**：不需要任何外部 API Key，不需要任何脚本。Agent 直接读写 JSON 文件完成所有操作。

## 数据存储

**数据文件路径**：`~/.workbuddy/data/job-applications.json`

每次操作时：
1. 用 Read 工具读取该 JSON 文件
2. 在内存中解析、修改数据
3. 用 Write 工具写回文件

如果文件不存在，初始化一个空数据结构（格式见 `references/data_model.md`）。

## 核心功能

根据用户输入，判断执行以下哪种操作：

### 操作一：新增投递

**触发**：用户说"我投了XX""我刚投了XX岗位""新增一个投递"等。

**步骤**：

1. 从用户消息中提取以下字段：
   - **公司**（必填）— 公司名称
   - **岗位**（必填）— 岗位名称
   - **部门**（选填）— 具体部门或业务线
   - **岗位详情**（选填）— JD 内容、岗位要求等
   - **投递渠道**（选填）— 官网/Boss直聘/内推/猎头等
   - **投递日期**（选填）— 默认为当天
   - **备注**（选填）— 其他信息

2. **字段校验**：
   - 必填字段（公司、岗位）缺失时，**必须反问用户**。
   - 反问示例："你投的是哪家公司的什么岗位？"
   - 选填字段缺失时，不追问，直接留空。

3. **查重**：
   - 检查是否已存在相同「公司+岗位」的活跃记录。
   - 如果存在，询问用户："你之前已经投过腾讯 IMA产品经理，是要更新这条记录，还是新建另一个岗位的投递？"

4. **写入数据**：
   - 生成递增 id（当前最大 id + 1，三位数补零）
   - 初始状态设为"投递"
   - 在 status_history 中添加第一条记录
   - is_active 设为 true，end_result 设为 null
   - 写入 JSON 文件

5. **输出确认**：
   - 以表格形式展示新增的记录
   - 简要提示"已记录，后续进度更新随时告诉我"

### 操作二：更新进度

**触发**：用户说"XX二面了""XX收到笔试通知""XX那个终止了""XX公司发offer了"等。

**步骤**：

1. **模糊匹配定位记录**（关键步骤，详见下方"模糊匹配规则"）：
   - 从用户消息中提取公司名称、岗位关键词等线索
   - 在 applications 数组中匹配活跃记录（is_active=true）
   - 确定要更新的目标记录

2. **提取状态信息**：
   - 从用户消息中提取新的状态/进度
   - 如果用户提到了一个不在 status_types 列表中的新状态，**自动将其添加到 status_types**（详见"动态状态管理"）
   - 提取日期（默认当天）、备注（如有）

3. **判断是否为终态**：
   - 如果用户表达的是"通过/拿到了/接受了 offer"→ end_result = "通过"，is_active = false
   - 如果用户表达的是"没过/被拒/终止/放弃了/撤回了"→ end_result = "终止"，is_active = false
   - 其他情况 → 更新 current_status，在 status_history 中追加记录

4. **写入数据**并**输出更新后的完整表格**

### 操作三：查看投递总览

**触发**：用户说"看看我的投递情况""现在有哪些在面""投递总览"等。

**步骤**：

1. 读取 JSON 文件
2. 输出 Markdown 表格，包含所有记录（活跃 + 已结束）
3. 可按用户要求筛选（如"只看在面的""只看腾讯的"）

**默认表格列**：

| 序号 | 公司 | 部门 | 岗位 | 当前状态 | 投递日期 | 终态 | 备注 |

### 操作四：查看单条详情

**触发**：用户说"XX那个的详细情况""XX面试进度"等。

**步骤**：

1. 模糊匹配定位记录
2. 输出该记录的完整信息，包括完整的 status_history 时间线

### 操作五：从邮件同步进度

**触发**：用户说"从邮件更新进度""同步一下面试邮件""看看邮件里有没有面试通知"等。

**依赖**：`email-interview-organizer` skill（已安装）

**完整步骤**：

1. **拉取并处理邮件**：
   - 加载 `email-interview-organizer` skill
   - 执行其第 1-2 步（获取邮件 → 过滤精简），得到招聘相关邮件列表
   - 每封邮件已包含：公司、部门/岗位线索、邮件类型（面试/测评/offer/拒绝等）、时间、关键链接

2. **逐封匹配投递记录**：
   - 读取 `~/.workbuddy/data/job-applications.json`
   - 对每封邮件，使用本 Skill 的模糊匹配规则，在活跃记录中查找对应投递
   - 匹配线索来源：邮件中提取的公司名、部门名、岗位名
   - 匹配结果：
     - 恰好匹配 1 条 → 继续步骤 3
     - 匹配 0 条 → 告知用户"收到 XX 公司的面试邮件，但投递记录中没有这家公司的投递，是否要新建？"
     - 匹配多条 → 反问用户确认是哪条记录

3. **推断状态更新**（详见"邮件联动 → 邮件类型与状态映射"）：
   - 根据邮件类型和内容，推断应该更新到什么状态
   - 如果邮件明确提到轮次（如"二面通知"），直接使用
   - 如果未明确，根据 current_status 推断下一轮
   - 如果是 offer 邮件，更新为"Offer"并询问是否标记"通过"
   - 如果是拒绝邮件，标记为"终止"

4. **写入数据并输出同步报告**：
   - 更新所有匹配成功的记录
   - 输出同步报告表格
   - 继续执行 email-interview-organizer 的第 3-4 步（创建飞书日程/任务 + 汇总报告）

**同步报告格式**：

```
## 邮件同步报告

> 同步时间：{当前时间}
> 检查邮件：{count} 封招聘相关邮件

| # | 公司 | 岗位 | 邮件类型 | 状态变更 | 匹配结果 |
|---|------|------|---------|---------|---------|
| 1 | 腾讯 | IMA产品经理 | 面试通知 | 二面 → 三面 | ✅ 已更新 |
| 2 | 字节跳动 | 后端开发 | 测评邀请 | — | ⚠️ 未找到投递记录 |
| 3 | 阿里 | 产品经理 | offer | Offer → 通过 | ✅ 已更新 |
```

## 模糊匹配规则

这是本 Skill 的核心能力。用户更新进度时，提供的信息可能不完整，需要智能匹配。

### 匹配流程

```
第 1 步：提取线索
  从用户消息中提取所有可能的线索：公司名、部门名、岗位关键词、业务线名称等
  示例："腾讯那个二面了" → 线索：公司=腾讯
  示例："ima那个收到offer了" → 线索：关键词=ima
  示例："CSIG的产品岗终止了" → 线索：部门=CSIG, 关键词=产品

第 2 步：在活跃记录中筛选
  只在 is_active=true 的记录中匹配
  按以下优先级逐级筛选：
  ① 精确匹配公司名（如"腾讯" == "腾讯"）
  ② 模糊匹配公司名（如"腾讯" 包含/被包含于 "腾讯控股"）
  ③ 匹配部门名（如"CSIG" 包含于 department 字段）
  ④ 匹配岗位关键词（如"产品" 包含于 position 字段）
  ⑤ 匹配 job_detail 中的关键词（如"ima" 出现在岗位详情中）

第 3 步：判断匹配结果
  - 恰好匹配 1 条 → 直接操作，输出时说明"已匹配到：腾讯 IMA产品经理"
  - 匹配 0 条 → 告知用户"没找到对应的投递记录"，列出所有活跃记录供参考，询问是否要新建
  - 匹配多条 → 必须反问
```

### 反问示例

当匹配到多条记录时：

> 你有腾讯的以下活跃投递，请问是哪个？
> 1. 腾讯 CSIG - IMA产品经理（当前：二面）
> 2. 腾讯 WXG - 后端开发（当前：笔试）

用户回复序号或岗位名后，继续操作。

### 匹配注意事项

- **不区分大小写**：用户说"ima"能匹配到记录中的"IMA"
- **支持简称/俗称**：用户说"字节"能匹配到"字节跳动"
- **支持业务线名称**：用户说"ima那个"能匹配到 position 或 job_detail 中包含"ima"的记录
- **宁可反问，不要猜错**：当无法确定唯一记录时，必须反问

## 动态状态管理

### 初始状态类型

数据文件初始化时包含以下状态类型：

```
投递、笔试、AI面试、一面、二面、三面、四面、HR面、Offer
```

### 新增状态类型

当用户提到一个不在 status_types 列表中的状态时，**自动将其添加到 status_types**，并正常记录。

示例场景：
- 用户说"XX要做性格测试" → 新增"性格测试"到 status_types
- 用户说"XX要做群面" → 新增"群面"到 status_types
- 用户说"XX要做一个项目作业" → 新增"项目作业"到 status_types
- 用户说"XX安排了加面" → 新增"加面"到 status_types

### 终态处理

终态有两种，不加入 status_types，而是单独标记：

| 终态 | 触发表达 | 含义 |
|------|---------|------|
| 通过 | "拿到了""发offer了""接受了""入职了""过了" | 成功拿到 offer 或已入职 |
| 终止 | "没过""被拒了""终止了""放弃了""撤回了""泡池子了""流程结束了" | 流程结束未拿到 offer |

标记终态时：
- `is_active` 设为 `false`
- `end_result` 设为 "通过" 或 "终止"
- `current_status` 保留最后一个状态不变
- 在 `status_history` 中追加终态记录，note 中记录具体原因（如"二面未通过""主动放弃"）

## 邮件联动

本 Skill 可与 `email-interview-organizer` skill 联动，自动从面试邮件中提取进度信息并更新投递记录。

### 邮件类型与状态映射

当从邮件同步进度时，根据邮件内容判断状态更新：

| 邮件类型 | 关键词/特征 | 状态更新逻辑 |
|---------|-----------|-------------|
| 面试通知（明确轮次） | "二面""三面""HR面""终面""加面" | 直接使用邮件中提到的轮次 |
| 面试通知（未明确轮次） | "面试通知""面试邀请" | 根据当前状态推断下一轮（见下方推断规则） |
| 测评/笔试通知 | "测评""笔试""性格测试""能力测试" | 新增对应状态（如"测评""性格测试"），或使用"笔试" |
| AI 面试通知 | "AI面试""视频面试""录制面试" | "AI面试" |
| offer 通知 | "offer""录用""入职通知""发放 offer" | 更新为"Offer"，询问用户是否标记为"通过" |
| 拒绝/结束 | "感谢""遗憾""未通过""不予录用""流程结束" | 标记为"终止"，note 记录原因 |
| 其他 | — | 不更新状态，仅将邮件要点追加到记录的 notes 字段 |

### 面试轮次推断规则

当邮件说"面试通知"但没明确第几轮时，根据 current_status 推断：

| 当前状态 | 推断的下一轮 |
|---------|-------------|
| 投递 | 一面 |
| 笔试 | 一面 |
| AI面试 | 一面 |
| 一面 | 二面 |
| 二面 | 三面 |
| 三面 | 四面 |
| 四面 | HR面 |
| HR面 | 不推断，询问用户 |

推断后应告知用户："根据当前进度（一面），将更新为二面，如不正确请告诉我。"

### 邮件联动的触发方式

用户可以通过以下方式触发邮件同步：
- "从邮件更新进度" / "同步面试邮件" / "看看邮件里有没有面试通知"
- 也可以在 email-interview-organizer 处理完邮件后，自动询问用户"是否同步更新投递追踪表？"

### 注意事项

1. **邮件同一天内可能有多封**：同一公司同一天可能先发测评再发面试通知，按时间顺序依次更新
2. **避免重复更新**：如果 status_history 中已有同一天同状态的记录，跳过不重复添加
3. **邮件可能是群发模板**：注意从邮件正文和发件人中准确提取公司信息，不要被模板内容误导
4. **匹配失败不阻塞**：某封邮件匹配不到投递记录时，不阻塞其他邮件的同步，在报告中标注即可

## 特殊情况处理

### 用户信息严重不足

当用户只说"更新一下"或"记一下"而没有任何线索时：
> 你想做什么操作？
> 1. 新增投递 — 告诉我公司、岗位等信息
> 2. 更新进度 — 告诉我哪家公司、什么进度
> 3. 查看总览 — 我把所有投递列出来

### 数据文件不存在或为空

首次使用时，初始化数据文件：
```json
{
  "version": 1,
  "last_updated": "<当前时间>",
  "status_types": ["投递", "笔试", "AI面试", "一面", "二面", "三面", "四面", "HR面", "Offer"],
  "applications": []
}
```

### 用户要删除记录

一般不删除，建议标记为终止。如用户坚持删除，确认后从 applications 数组中移除。

### 用户要修改已有记录的非状态字段

如"把腾讯那个的岗位名改一下""投递渠道写错了"，直接匹配记录并更新对应字段。

## 设计原则

1. **对话优先**：所有操作通过自然语言完成，不需要固定格式输入
2. **模糊但准确**：允许用户说得模糊，但匹配不确定时必须反问，不能猜错
3. **状态灵活**：不预设固定流程，支持任意状态类型，随时可扩展
4. **数据透明**：所有数据存在本地 JSON 文件，用户可随时查看、备份、迁移
5. **反馈清晰**：每次操作后输出表格确认，让用户清楚当前状态
